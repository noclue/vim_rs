# Research: vSphere 9.1.0.0 API Binding Update

**Feature**: [spec.md](./spec.md)  
**Date**: 2026-06-26

Each item: **Decision**, **Rationale**, **Alternatives considered**.

---

## R1 — Canonical OpenAPI input file

**Decision**: Use `vim_build/data/vi_json_openapi_specification_v9_1_0_0.json` as the sole generator input for this release (FR-001, FR-012).

**Rationale**: User has already converted `vi-json.yaml` to JSON via `yq -o=json`. JSON is the canonical ingestion format per constitution OpenAPI ingestion standard. Prior 9.0.x file may remain for reference but must not be used by the generator.

**Alternatives considered**:

- **Keep 9.0.x as input, cherry-pick 9.1 changes** — rejected (violates Principle I; defeats purpose of spec tracking).
- **Generate directly from YAML** — rejected (project convention is JSON input; YAML is source-of-truth archive only).

---

## R2 — Generation workflow

**Decision**: Single clean run of `vim_build` generator:

```bash
cd vim_build
cargo run --bin generate --release
```

This invokes `emit_vim_bindings()` which emits `vim_rs/src/` bindings plus `field_data.rs` for both `vim_macros` and `mcp/server` in one pass (`generator.rs`).

**Rationale**: Guarantees FR-002/003/004/005 — all artifacts from the same `vim_model::Model`. Matches documented workflow in `CLAUDE.md`.

**Alternatives considered**:

- **Separate field_data generation tool** — rejected (no such tool; field data is part of `emit_vim_bindings`).
- **Incremental/partial regeneration** — rejected (risk of drift between surfaces; full regen is standard for spec bumps).

---

## R3 — OpenAPI input validation & failure triage

**Decision**: Pre-flight and on-failure validation prioritizes **spec correctness** (FR-013):

1. Confirm JSON parses via `openapi30` / generator load step.
2. Verify known coercion pitfall: `DatastoreAccessible_enum` values are strings `"True"`/`"False"`, not JSON booleans.
3. On any generator/compile/test failure, inspect YAML source and JSON conversion output **in parallel with** (not after) generator debugging.

**Rationale**: Prior vSphere updates failed when YAML `true`/`false` were coerced to booleans per YAML semantics. Spec clarification (2026-06-26) mandates this triage order. Pre-check on supplied 9.1.0.0 JSON shows `DatastoreAccessible_enum` already correct:

```json
"enum": ["True", "False"]
```

**Alternatives considered**:

- **Patch generated output when spec is wrong** — rejected (Principle I).
- **Add generator workarounds for boolean enums** — rejected unless spec is authoritative and correct; fix input instead.

## R4 — Hard-coded spec path updates

**Decision**: Update all references from `vi_json_openapi_specification_v9_0_0_0_24798170.json` to `vi_json_openapi_specification_v9_1_0_0.json` in:

| Location | Role |
|----------|------|
| `vim_build/src/main.rs` | Generator entry |
| `mcp/data_processing/data_transformer/src/main.rs` | MCP database builder |
| `mcp/server/build.rs` | Staleness check / `rerun-if-changed` |
| `openapi30/src/openapi.rs` | Test fixture (`include_str!`) |
| `vim_build/src/vim_model/loader.rs` | Loader unit test |

**Rationale**: Stale paths would leave MCP/tests on 9.0.x while bindings target 9.1.0.0 — silent drift violating FR-005 and SC-007.

**Alternatives considered**:

- **Shared constant crate** — rejected (out of scope; path strings are existing pattern).
- **Environment variable for spec path** — rejected (no existing infra; YAGNI for one-time bump).

## R5 — MCP rebuild sequence

**Decision**:

1. Regenerate bindings + field_data (R2).
2. `cd mcp && cargo run -p data-transformer --release --features cuda` → writes `mcp/data/api_database.bin`.
3. `cargo build --release -p vim_mcp_server` (validates database freshness via `build.rs`).

**Rationale**: MCP server embeds/validates against `api_database.bin` built from OpenAPI + examples. Field_data in `mcp/server/src/` is generated by vim_build but semantic search DB is separate pipeline per `mcp/README.md`. Use `--features cuda` on machines with NVIDIA GPU to accelerate embedding generation (clarification 2026-06-26).

**Alternatives considered**:

- **Skip MCP rebuild** — rejected (FR-005, SC-007, Principle VII).
- **Manual field_data only** — rejected (database still stale without data-transformer).

## R6 — Version bump scope

**Decision**: Bump to **0.6.0** (minor breaking release — **not** 0.5.1) in:

- `vim_rs/Cargo.toml` (`version` + `vim_macros` dep)
- `vim_macros/Cargo.toml` (`version`)
- `examples/snippets/Cargo.toml`, `examples/vtui/Cargo.toml` (path dep version strings)
- `CHANGELOG.md` — retitle any `[0.5.1]` draft to `[0.6.0]`
- `mcp/README.md` — version alignment mention
- In-repo spec kit artifacts under `specs/003-vsphere-910-update/` (FR-015)

Do **not** bump MCP sub-crate versions (0.1.0 internal tooling) unless dependency breakage requires lockfile-only updates.

**Rationale**: FR-006/007/015 and spec clarification (2026-06-26): 9.1.0.0 spec diff introduces compile-breaking struct changes (e.g. new `EventFilterSpec` fields) that require consumer source updates without the `defaults` feature — a minor semver bump is correct. Version 0.5.1 MUST NOT be published.

**Alternatives considered**:

- **0.5.1 patch bump** — rejected (superseded by clarification; understates breaking VIM surface changes).
- **Bump all workspace versions** — rejected (unnecessary churn for internal MCP tooling).

## R7 — Build-time & binary-size metrics (Principle III)

**Decision**: Before/after capture for release notes:

```bash
# Debug build time (representative)
cd vim_rs && cargo build 2>&1 | tail -1

# Release build time
cd vim_rs && cargo build --release 2>&1 | tail -1

# vtui binary size

# measure target/release/vtui.exe (or vtui on Unix)
```

Compare against 0.5.0 baseline; document in CHANGELOG if regression exceeds project tolerance.

**Rationale**: SC-008 and constitution release gate. Spec growth (9.0 → 9.1) may increase generated LOC and compile time — expected but must be measured.

**Alternatives considered**:

- **Skip metrics for patch release** — rejected (constitution NON-NEGOTIABLE on build budgets).

## R9 — Semver classification (0.6.0 minor breaking)

**Decision**: Classify this release as **0.6.0 minor breaking**, not 0.5.1 patch. Document exemplar breaks in CHANGELOG:

- **`EventFilterSpec`**: new fields `auditable`, `audit_id` — existing struct literals fail without `defaults` feature or explicit field assignment.
- Additional spec-driven renames/removals discovered during compile validation MUST be listed under `[0.6.0]`.

**Rationale**: Pre-1.0 semver still signals intent: additive VIM fields on generated structs are compile-breaking for consumers using struct literals. Minor bump sets correct upgrade expectations (FR-011, SC-006).

**Alternatives considered**:

- **0.5.1 patch with CHANGELOG-only break notes** — rejected (semver would understate impact; 0.5.1 MUST NOT ship).
- **1.0.0 major** — rejected (project remains pre-1.0; API binding updates are expected to evolve).

## R8 — `PRUNED_TYPES` policy

**Decision**: Keep `PRUNED_TYPES = ["MethodFault", "Event"]` unchanged unless generator fails on new 9.1.0.0 constructs.

**Rationale**: Spec assumption; established project policy. Expanding pruned types would be a separate feature decision.

**Alternatives considered**:

- **Expand pruned types preemptively** — rejected (scope creep; only if blocking).
