# Implementation Plan: MCP Performance Counters

**Branch**: `007-mcp-perf-counters` | **Date**: 2026-10-25 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/007-mcp-perf-counters/spec.md`, plus Part II of `docs/vim_rs-perf-mcp.md` (v4.2). `docs/**` is gitignored. This plan and its sibling artifacts are the tracked design. Normative id, unit, scope, and synonym tables stay in [spec.md](./spec.md) and are not restated here.

**Spec-quality checklist**: `checklists/requirements.md` leaves two “no implementation details” boxes open on purpose (the counter contract is the subject matter). That is not a constitution-gate failure.

## Summary

Index the catalog description on each generated counter constant in `vim_rs/src/perf/metrics.rs`, and teach `vim_rs::perf` through the starter guide and the performance examples. Counters are not embedded in the MCP vector index: semantic search cannot separate counters that share the words CPU, usage, and percentage. `plan_counters` remains the read-only planner the emitter calls. The two-problem evaluation extends the harness in `mcp/evals/`. A miss is recorded. It does not block release.

## Technical Context

**Language/Version**: Rust 2021, `rust-version = "1.86"` (`vim_rs` 0.6.1 today; next release 0.7.0). Python 3 for the evaluation scorecard. Operator commands are `mcp/evals/runner/grade.ps1` and `run_matrix.ps1`.

**Primary Dependencies**: Existing MCP stack (`serde`, `serde_json`, `bincode` serde, `indexmap`, `chrono`, `anyhow`, `tracing`, `schemars`, BGE-small-en-v1.5 via the current embedding crate). `build_counters` adds a path dependency on `vim_build` and on `api_database`. `vim_rs` gains no dependency. `api_database` must not depend on `vim_build`.

**Storage**: Embedded `mcp/data/api_database.bin` (bincode serde). Debug JSON `mcp/data/api_definitions/counters.json` only when `data-transformer --emit-json` runs. ESXi catalog committed at `vim_build/data/esxi-perf-catalog.json`, byte-identical to `vim_rs/tests/fixtures/perf/esxi_catalog.json`. No counter sidecar under `vim_build/data/`.

**Testing**: Hermetic `cargo test -p api_database`, `cargo test -p build-counters`, `cargo test -p build-examples`, `cargo test -p vim_build`, `cargo test -p vim_rs --features perf`. `cargo check -p snippets --bins` from `examples/`. Model-backed ranking is `cargo test -p vim_mcp_server -- --ignored` and is not part of the default offline run. Evaluation grading is `mcp/evals/runner/grade.ps1` on the harness in this tree.

**Target Platform**: Offline MCP server binary (the index is embedded). Generator and pipeline are host tools. Snippets run against a live vCenter at release time, the same gate as the other snippets.

**Project Type**: Documentation pipeline plus generator rustdoc, example programs, and a later evaluation slice. Not a change to the `vim_rs::perf` runtime.

**Performance Goals**: Counter lookup is three hash-map steps after the alias index is built once. Search stays the existing embedding ranking. The server tool list stays at 6. Step 5 of the starter guide is at most 40 lines.

**Constraints**: Do not edit generated constant names, dimensions, scopes, or `by_entity` re-exports by hand. Do not add `serde` to `vim_rs`. Do not add an MCP tool. Do not connect the server to vCenter. Do not release the updated server before `vim_rs` 0.7.0 is published. `api_database` stays free of a `vim_build` dependency.

**Scale/Scope**: 732 generated counter constants with catalog descriptions in rustdoc. Five `perf_*` snippet binaries. Two evaluation problems (`pf01_vm_balloon_costop_query`, `pf02_vm_electricity_turn_query`). Counters are not embedded in the MCP vector index.

## Phase 1: Design

**Status**: Complete → [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

### Pipeline

`data-transformer` becomes five steps: API definitions, examples, counters, `ApiData::from_parts`, embeddings. Counters are collected in memory. `counters.json` is written only for `--emit-json`. `ApiDatabase` gains a `#[serde(skip)]` `OnceLock` alias index so the bin file stays a pure item-and-embedding blob. The struct literal in `data_transformer` sets `counter_aliases: Default::default()`.

### What does not move

`vim_rs::perf` query, decode, watermark, and scope behavior stay as specified in `specs/006-perf-manager-api`. This plan only publishes `plan_counters` and changes rustdoc. OpenAPI extraction does not learn about `vim_rs::perf` types.
